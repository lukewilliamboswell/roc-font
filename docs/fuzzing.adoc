= Fuzzing roc-font
:toc: left
:toclevels: 2

This chapter is for contributors. It explains what each fuzz target
promises, how to run the targets, where their inputs come from, and what to
do with a failure. The reasons behind fuzzing as a verification layer are
in architecture §7.3; the rule that every reading or shaping stage gets a
target is in `AGENTS.md` ("Verify the contract").

== Why fuzz a font library

Font bytes are hostile input. Unit expects check the cases someone thought
of; fuzzing checks the contract on inputs nobody thought of: truncated
tables, offsets that point outside the file, counts that overflow, lookups
that recurse, runs that grow. A successfully read font must make every
later query and shaping call total (architecture §3), and only generated
input tests that claim at scale.

== Targets and their contracts

Each target is a roc-fuzz app built natively with `roc build --fuzz`. Its
`test!` function crashes, with a message naming the broken promise, when
the contract does not hold. `python3 scripts/run_fuzz.py list` prints the
current list.

[cols="1,3,3",options="header"]
|===
|Target |Input |Contract

|`font-read`
|A font file (input starting with a font signature: `00 01 00 00`,
`OTTO`, `true` or `ttcf`), or a recipe read by `FontBuild.fuzz_font`: the
first byte picks a base (Inter, the synthetic sample, the sample cut short,
or nothing) and each following four bytes patch one byte. The same bytes
choose the contents of `FontBuild.scaled` fonts.
|Reading never crashes and is deterministic (two reads give identical
results). A rejection names at least one problem. An accepted font has
finite metrics, `units_per_em` in 16..16384 and at least one glyph;
character lookups give glyphs the font has; advances are finite and
non-negative; outline extents are finite and ordered; kerning gives one
finite value per glyph; substitution keeps clusters inside the run and
gives at most `4 n + 32` glyphs. Queries are probed past the font's own
glyph range, at plane edges and with empty runs.

|`font-shape`
|UTF-8 text (invalid sequences replaced), optionally a `0xFF` byte and a
font or recipe as `font-read` takes it. Without a readable font the text is
shaped with Inter.
|Substitution is deterministic, keeps every cluster inside the run, and
gives at most `4 n + 32` glyphs and at most 36 per character. Kerning gives
one finite value per glyph. A run's width (advances plus kerning) is
deterministic and finite.

|`font-cmap`
|A choice byte (the character map format: 0, 4, 6, 10, 12 or 13; glyph
arrays or deltas for format 4; code points past U+FFFF for 10 and 12; a
final range drawn by a glyph past the font for 4, 12 and 13), then up to
32 bytes, each choosing one range of the map (gap, length, first glyph,
sometimes glyph 0). The maps follow what OTS accepts: formats 0, 6 and 10
sit beside an empty format 4 map (they outrank it, and may name glyphs
past the font); formats 4, 12 and 13 name only glyphs the font has.
|Both sizes read strictly (with a glyph past the font, both are refused
with one problem, a bad `cmap`). Every lookup of every range's characters,
their neighbours and plane edges agrees with the map the recipe describes;
the code point listing is that map, ascending; two reads agree.

|`font-ots`
|A choice byte (the damaged table: `head`, `cmap`, `GSUB`, `post` or
`name`; the `post` version; a format 1 naming table; whether the table is
cut short), then three-byte patches (a position in the damaged table and
its new value) applied to a valid font with all five tables.
|The undamaged fonts read strictly in full. Reading a damaged font is
deterministic; strict reading succeeds exactly when lenient reading
succeeds with nothing dropped; every problem names exactly the damaged
table. An accepted font's lookups, listings, advances, extents, glyph and
family names and shaping are total and keep their promises.

|`font-coverage`
|A choice byte (coverage format, single substitution format, both class
definition formats, class counts), then up to 32 bytes choosing runs of
covered glyphs, kerning values and the text.
|With kerning off the glyphs are the text's, with exactly the covered ones
substituted as the recipe says; with ligatures off the width is the
advances plus the class kerning of every adjacent pair whose first glyph
is covered. Runs are index-aligned with clusters in range.

|`font-gsub`
|A choice byte (lookup type 1, 2, 4, 5, 6, or 7 holding 1, 2 or 4), then
two bytes per lookup choosing its coverage, format, outputs and context.
Lookup `i` reads only its own band of eight glyphs and writes only glyphs
1 to 15.
|With ligatures off the glyphs are the text's. Both sizes give the same
run (the extra lookups never match the text), deterministically, with
clusters in range and in order and growth within HarfBuzz's bound.

|`font-gpos`
|A choice byte (`GPOS` pair format 1 or 2, or `kern`, and class counts),
then up to 32 bytes choosing each first glyph's pairs and the text.
|The glyphs are the text's; the width is the advances plus the recipe's
kerning of every adjacent pair; both sizes give the same run; runs are
index-aligned with clusters in range and in order.

|`font-var`
|A choice byte (1 to 4 axes, 2 to 5 regions, `OS/2`, an `HVAR` index map,
raw maps and regions), 48 bytes choosing axes (tags may repeat), `avar`
maps, regions, deltas and the metrics `MVAR` varies, then up to eight
locations of eight bytes (named weights and widths, optical sizes, axis
values: huge, fractional, for tags the font lacks).
|Both sizes read; unless raw, nothing is dropped and the axes are those
built. `at` and every query on its result are total and deterministic;
advances are finite, never negative and 0 past the font; every axis at its
default gives the `hmtx` advances; every glyph and metric of the smaller
font measures the same in the larger at every location.

|`font-gvar`
|A choice byte (1 to 3 axes, long `loca` and `gvar` offsets, short
horizontal metrics, side bearings away from the outlines), 48 bytes
choosing 16 glyphs (empty, simple with one to three contours, composites
nested up to four deep) and their `gvar` tuples (shared or embedded peaks,
intermediate regions, shared, all or private points, phantom points), then
up to four locations of four bytes.
|Both sizes read strictly in full. `extents` is total and deterministic,
`Empty` for the empty glyph and past the font. At the default location it
is the header-box rule (left edge at the side bearing, the header's width
and heights). Where every coordinate is -1, 0 or 1 it equals a model of
the recipe (each tuple moves by its whole delta or not at all, every point
of a contour or component it touches, measured from the moved left phantom
point); elsewhere a glyph without variations keeps its default box and
every edge of any other stays within twice its deltas of it. Both sizes
measure the smaller font's glyphs the same.

|`font-layout-var`
|A choice byte (1 to 3 axes, value records with or without a stored
advance, `GSUB` lookup variation records, `GPOS` feature variations,
and/or/not conditions, class counts), 48 bytes choosing the `GDEF` store's
single-axis regions and deltas, three pair kerning lookups (formats 1, 2,
1) with `VariationIndex`, no-variation and hinting devices, the lookups of
`kern`, `calt` and `rvrn`, feature and lookup variation records and the
text, then up to four locations of four bytes.
|Both sizes read strictly in full. Shaping is deterministic, index-aligned
and gives exactly the model's glyphs and width at every location: each
substitution applies exactly where the first matching feature variation
record and the lookup variation records say, and each kerned pair adds the
stored value plus its device's delta (region scalars, exact because every
region spans a power of two, weighted by the deltas, rounded half up;
nothing for hinting devices or at the default location). Both sizes give
the same run.
|===

The last eight are *narrow* targets (architecture §7.3): the input chooses
the contents of a font that exercises one feature, built with `FontBuild`
at two sizes, so a failure names its cause. The sizes are 2 and 16 copies
of the chosen items (`font-cmap`, `font-coverage`, `font-gpos`), 8 and 64
lookups (`font-gsub`), 32 and 256 glyphs with 8 times the regions
(`font-var`), 16 and 128 glyphs with 8 times the shared tuples
(`font-gvar`), 24 and 192 glyphs with 8 times the regions, pairs,
substitution lookups and (never matching) feature variation records
(`font-layout-var`), and 32 and 256 glyphs with 8 times the character
map ranges, substitution lookups, stored glyph names and name records
(`font-ots`). Each builds valid fonts only (apart from `font-var`'s raw
mode, `font-cmap`'s glyph past the font and `font-ots`'s damage), so it
can compare against what the recipe means: a differential check against
the builder, without an oracle. `font-ots` instead checks the reading
checks ported from OTS 9.3.0 (architecture §4.4): a damaged table is
either accepted, and then every query is total, or refused naming that
table alone. The recipes
of `font-gvar` and `font-layout-var` are chosen so that the model is exact
in integers: `font-gvar` checks its model where every coordinate is -1, 0
or 1 (every tuple's scalar is then 0 or 1) and bounds elsewhere, and
`font-layout-var` uses regions on one axis whose sides span a power of
two, so every scalar is an exact binary fraction at any location. Real font files are not
their seeds, and they use `fuzz/dictionaries/narrow.dict`.

Every target also checks *cost*:

* *Allocation linearity.* `Fuzz.measure_allocs!` counts the allocations of
  the operation at two sizes: reading `FontBuild.scaled` fonts built from 2
  and 16 copies of the input's choices, and shaping the text repeated 2 and
  16 times. The larger may take at most `10 × small + 256` allocations: an
  8-fold input with headroom for constant overhead. Quadratic behaviour
  (a list copied per item, a sort on sorted input) fails quickly. The
  narrow targets apply the same bound to reading their two fonts, to
  planning (`font-gsub`, linear in lookups) and to listing code points
  (`font-cmap`). `font-ots` compares reading the larger damaged font with
  reading the smaller one undamaged, in full, so damage that makes
  reading allocate more than its size accounts for fails.
* *Constant cost per call.* The narrow targets also run one query or
  shaping call on both fonts with the same arguments: character lookups
  (`font-cmap`), `shape_planned` on the same text with a plan made
  beforehand (`font-coverage`, `font-gsub`, `font-gpos`,
  `font-layout-var`), `at` and advance lookups at the same location
  (`font-var`), and `at` and the extents of the smaller font's glyphs
  (`font-gvar`). The larger font may take at most 8 more allocations (4
  for `font-var` and `font-gvar`) than the smaller: per-call work must not
  grow with the font's tables. On the seeds, lookups take 0 allocations at
  both sizes, shaping 10 to 14, `at` 5 to 18, and the extents of 16 glyphs
  515 to 924 (the same at both sizes). `font-layout-var` also measures
  planning at one location: planning evaluates every feature variation
  record before the one that matches on one reused stack, so the larger
  font's 7 extra records must add no allocations.
* *Leaks.* `Fuzz.expect_no_leaks!` runs the larger operation and fails if
  anything it allocated is still live afterwards. roc-fuzz also checks
  every input for leaks unless `--no-detect-leaks` is passed; the scripts
  never pass it.

=== Planned targets

Architecture §7.3 calls for more targets as the stages they cover land:
narrow targets for the stages not yet covered (mark positioning, cluster
levels), and a differential target that shapes fuzzed text on
corpus fonts and compares with recorded HarfBuzz output. A new stage is
not finished until its target exists, is seeded and is registered in
`scripts/run_fuzz.py`.

== Layout

The targets live in `fuzz/` as `<target>.roc`. They name the package as
`../package/main.roc`, but `run_fuzz.py` always builds them against the
`roc bundle` output, exactly what ships: it bundles the package, serves
the bundle from a loopback address (`scripts/flight.py`) and passes
`--replace-dep ./package/main.roc <url>` to `roc build --fuzz`, so they
exercise the artifact every consumer imports (`--source` compiles
`package/` directly, for quick local iteration only). The byte builders they need
live in a separate test-only package, `tests/support/` (module
`FontBuild`), which imports nothing from roc-font:

[source,roc]
----
app [target] {
	build: "../tests/support/main.roc",
	font: "../package/main.roc",
	fuzz: platform "<pinned roc-fuzz URL>",
}

import build.FontBuild
import font.Font
----

`package/main.roc` never reaches `tests/support/`, so `roc bundle` and
`roc docs` are unchanged. The unit tests of the public API in `tests/api/`
import the same two packages. A symlinked module does not work on the
current nightly ("resolves outside this package's source root").

Everything else lives in `fuzz/`:

----
fuzz/
  <target>.roc              roc-fuzz targets
  seeds/<target>.json       reviewed starting inputs, each with a reason
  dictionaries/font.dict    tags, signatures and edge values
  dictionaries/narrow.dict  choice bytes for the narrow targets
scripts/run_fuzz.py         build, seed, run, harvest
----

== Running

The scripts use `$ROC`, or `roc` on `PATH`. Use the compiler pinned in
`.roc-version`: different compiler builds can disagree, and a fuzz binary
is always native.

[source,sh]
----
python3 scripts/run_fuzz.py smoke                  # every target, seed 1
python3 scripts/run_fuzz.py smoke font-cmap font-var  # some targets
python3 scripts/run_fuzz.py smoke font-shape --runs=20000
python3 scripts/run_fuzz.py campaign --seconds=600 # each target, persistent corpus
python3 scripts/run_fuzz.py nightly                # 1800 s per target
python3 scripts/run_fuzz.py check-pin              # targets use the pinned roc-fuzz
----

`smoke` starts each target from a fresh corpus holding only the seeds,
runs 4000 inputs (1500 for `font-gvar`, `font-layout-var` and
`font-ots`, whose every input builds, reads and checks several fonts; `smoke_runs` in
`TargetConfig`, overridden by `--runs`) and passes a fixed libFuzzer seed, so its result depends only on the sources,
seeds, fonts present and compiler. It is the CI check and runs as a step of
`scripts/all_tests.py`. `campaign` and `nightly` grow one persistent corpus
per target and are for finding new failures.

Each run uses the target binary's supervised `ci` command, which records
provenance (commit, compiler version, roc-fuzz release and bundle digest)
and keeps evidence even when the target crashes. Working state goes under
the ignored `.roc-font-tmp/fuzz/` (or `$ROC_FONT_TMPDIR/fuzz/`):

----
bin/<target>              built binaries
corpus/<target>/          campaign corpus
smoke-corpus/<target>/    recreated for each smoke run
runs/<target>/<mode>/     report.json, summary.md, run.log, failures/
crashes/<target>/<sha256> harvested failure inputs
----

The roc-fuzz platform is pinned by release, bundle hash and asset SHA-256
in `ROC_FUZZ_RELEASE` in `scripts/run_fuzz.py`. Every target must declare
exactly that platform URL; `check-pin` (and every run) verifies it, and
verifies the cached download's digest when it is present. To upgrade,
change the URL in every target and the record in the script together.

== Seeds and corpus

A seed is useful when it reaches behaviour other seeds do not. Each entry
in `fuzz/seeds/<target>.json` says why it is there, and is built from
parts: `{"text": ...}` (UTF-8), `{"hex": ...}` or `{"file": ...}` (a path
under the repository). Because the targets read recipes, a few bytes can
stand for a nearly valid font; keep hand-written seeds small.

`run_fuzz.py` also adds every `.ttf`, `.otf`, `.ttc` and `.otc` file found
in `tests/fonts/` and in the fetched corpus `tests/corpus/` (architecture
§7.2; fetch it with `scripts/fetch_corpus.py`) to the targets that read
whole fonts (`font-read`, `font-shape`; `font_files` in `TargetConfig`). `font-shape` gets each font
after a short text and the `0xFF` marker. Files larger than the target's
input bound (256 KiB) are skipped and counted. The narrow targets take
short inputs (64 to 128 bytes) and only their reviewed seeds. When `tests/corpus/` is
absent, runs still work from the committed fixtures and say so.

The dictionary helps mutations produce table tags, signatures and boundary
values (`0xFFFF`, `0x8000`, common `unitsPerEm`) that random bytes rarely
hit.

== Distilling failures

A failing run prints the target's last lines and copies each reproducing
input to `.roc-font-tmp/fuzz/crashes/<target>/<sha256>`. Every failure
becomes a permanent unit expect before or with its fix; the fuzz corpus is
not a regression suite.

. *Show and replay* in a fresh process:
+
[source,sh]
----
python3 scripts/run_fuzz.py show font-read <input>
python3 scripts/run_fuzz.py replay font-read <input>
----
+
If replay does not reproduce, suspect a changed target or generator, a
truncated input, or a compiler difference before suspecting the library.
. *Minimise* it:
+
[source,sh]
----
python3 scripts/run_fuzz.py minimize font-read <input> .roc-font-tmp/fuzz/minimized/<name>
----
. *Distil* the minimal input into the smallest structure that still fails,
  preferably built with `FontBuild` so the test reads as a font, otherwise
  as literal bytes. Add it as a top-level `expect` in the public API test
  module for the stage (`tests/api/FontTests.roc` for reading and queries,
  `tests/api/SubstituteTests.roc` for substitution, and
  `tests/api/FuzzRegressionTests.roc` for failures of the narrow targets),
  going through `Font` as a consumer would. Only a failure the public API cannot observe goes in
  the package itself, as a top-level `expect` in the module that failed,
  built from inline bytes or a committed fixture, never the builders. Precede it with a doc comment that starts `## fuzz regression:` and names the
  target, the contract that broke and the cause:
+
[source,roc]
----
## fuzz regression: font-read. The sample font cut to 64 bytes, its table
## records pointing past the end, must be rejected with a problem.
expect
	match Font.from_bytes(FontBuild.sample.take_first(64)) {
		Err(problems) => problems.len() > 0
		Ok(_) => False
	}
----
+
. *Confirm* the expect fails before the fix and passes after, with both
  `roc test`.
. *Fix* the reader or shaper. If the target's contract itself was wrong,
  change the target and its doc comment in the same commit and say why.
. *Rerun* the target on its corpus to make sure nothing nearby still fails.

Do not commit crash inputs, corpora or run directories; only distilled
expects and reviewed seeds. A seed that represents an interesting fixed
crash may be added to `fuzz/seeds/` with its reason.

== Adding a target

. Write the target app with a doc comment stating its input format and its
  contract, and make every broken promise `crash` with a specific message.
. Include an allocation check at two sizes and `Fuzz.expect_no_leaks!` when
  the stage allocates in proportion to its input.
. Add `fuzz/seeds/<target>.json` and, if useful, a dictionary.
. Register it in `TARGETS` in `scripts/run_fuzz.py` with its input bound,
  timeout and a one-line contract; a narrow target, whose input is choices
  rather than a font file, sets `font_files=False`.
. Run `python3 scripts/run_fuzz.py smoke <target>` and a short campaign
  before landing it.
