= Conformance testing roc-font
:toc: left
:toclevels: 2

This chapter is for contributors. It explains how roc-font is compared with
reference implementations: the case format, the driver, the oracle records,
the review (gating and scored suites), the font corpus, curated imports from
HarfBuzz's test suites, and how to add cases, case sources and oracles. Why
conformance is shaped this way ("record once, replay cheaply") is in
architecture §7.1 and §7.2.

== Overview

Oracle tools (HarfBuzz, OTS, fontTools and Chrome) are not required for
normal checks. Each reference answer is recorded once, committed and
replayed by string comparison. The normal loop needs only Python's standard
library and a Roc compiler.

----
tests/cases/*.jsonc --> scripts/conformance.py --(line protocol)--> tools/driver (native Roc)
        |                   |      ^                                        |
        |                   |      +------------ one result per request ----+
        |                   +--> compare with records, known failures, scores
        +--> scripts/record_oracle.py --> tests/oracle/records/*.jsonl
                  (tools/oracle: uharfbuzz, OTS, fontTools; Chrome via Puppeteer)
----

Python is the driver: it parses the JSONC case files, normalises each case
and streams minimal requests to the Roc harness, which never sees JSON or
HarfBuzz's test syntax. HarfBuzz's `.tests` files are only an import source.

[cols="1,3",options="header"]
|===
|Path |Role

|`tests/cases/*.jsonc`
|Our own cases (the authority), in the JSONC case format below. Among them:
`default-fonts.jsonc` (the three default fonts at several locations),
`collections.jsonc` (faces of `ttcf` files), `corpus-fonts.jsonc` (the
pinned corpus fonts) and `chrome.jsonc` (Chrome widths).

|`tests/cases/hb-curated/`, `tests/cases/hb-pending/`, `tests/cases/hb-fonts/`
|Cases curated from HarfBuzz's suites: gating, scored (not passing yet), and
the small fonts the gating ones use. Generated from `tests/cases/curated.jsonc`.

|`tests/cases/harfbuzz/`
|The full HarfBuzz import (git-ignored, scored, regenerated on demand).

|`tests/cases/fixtures/`
|Tiny crafted fonts for unhappy paths, made by `generate.py`.

|`tests/oracle/records/<case file>.jsonl`
|One oracle record per case, committed (except for `harfbuzz/`).

|`tests/known-failures.json`
|Gating differences we accept for now, each with a reason.

|`tests/scores.json`
|Scored suites and their counts (a ratchet).

|`tests/corpus.json`, `tests/corpus/`
|Pinned external fonts; the fetched copies are not committed.

|`tools/driver/`
|The native Roc harness (`main.roc`, and `Case.roc` for the request
protocol and result notation, which has its own expects).

|`tools/oracle/`
|The oracle extractor (`extract.py`), its pinned libraries
(`requirements.txt`, with hashes), the pinned OTS build (`ots.json`) and the
Chrome width oracle (`chrome/`: `width.mjs`, `pin.json`, `package-lock.json`).

|`scripts/conformance.py`, `scripts/record_oracle.py`, `scripts/fetch_corpus.py`
|The review, the recorder and the corpus fetcher and importer;
`scripts/_common.py` holds the JSONC parser, the case normaliser, case ids,
record keys and the driver protocol they share.
|===

Nothing here is reachable from `package/main.roc`; the driver imports the
package, never the reverse. No `.roc` file is generated.

== Quick start

[source,sh]
----
export ROC=/path/to/roc                      # the latest Roc nightly

python3 scripts/conformance.py               # build the driver, run every case, compare
python3 scripts/conformance.py inter --diff  # one case file, with expected/actual

# Only when cases, fonts or oracle versions change:
python3 scripts/record_oracle.py --setup     # once: tools/oracle/.venv and ots-sanitize
python3 scripts/record_oracle.py             # record what changed
----

The review prints a summary such as:

----
416 gating cases in 9 files: 311 agree, 52 known, 0 fail, 0 stale, 0 missing-record, 0 missing-font, 0 font-changed, 0 bad-expectation, 53 unsupported, 0 skipped; 0 bad known-failure ids
scored hb-pending/M1-next: 16 cases, 0 agree, 12 differ, 4 unsupported, 0 skipped
...
driver: .roc-font-tmp/conformance/driver, 6117 requests in one process, 0.12 s; roc: ...
----

== Case format

=== JSONC

Case files are JSONC: JSON plus `//` line comments, `/* */` block comments
and trailing commas. `scripts/_common.py` strips comments outside strings
(keeping every character position, so error messages and line numbers match
the file) and parses the rest with Python's `json`.

A case file is an object:

[source,jsonc]
----
// Free-form comments explain the file.
{
  "schema": 1,                         // optional; only 1 exists
  "about": "…",                        // optional description
  "defaults": {                        // optional: fields every case takes unless it sets them
    "font": "../fonts/Inter-Regular-metrics.ttf"
  },
  "cases": [
    { "id": "kern-avatar", "text": "AVATAR", "expected": "[2=0+1273|456=1+1273|…]" },
    { "id": "ned", "text": "AVA", "options": { "output": ["ned"] }, "expected": "[2|456@1273,0|2@2546,0]" },
    { "id": "soft-hyphen-hidden", "unicodes": "U+0041,U+00AD,U+0042", "expected": "oracle",
      "reason": "default ignorables are hidden (architecture §6.2)" }
  ]
}
----

`defaults` merges into each case; an `options` object merges key by key, and
a case clears a default by setting the field to `null` (`font_sha256`,
`face`, `glyphs` and the location fields). Decimal numbers are parsed
exactly (as Python `Decimal`), so an axis value such as `87.5` reaches keys
and the driver as written. Every problem in a file is reported at once (unknown fields,
bad values, duplicate ids); a case with a problem is left out and the run
fails.

=== Case fields

[cols="1,1,4",options="header"]
|===
|Field |Required |Meaning

|`id`
|yes
|Unique within the file. The case's full id is `<file path under
tests/cases without .jsonc>/<id>`, for example `inter/kern-avatar`; records
and known failures use it. No spaces, `/`, `;`, `~`, `\` or quotes, and not
starting with `line-`.

|`kind`
|no (`shape`)
|`shape` (glyphs and positions), `read` (does the font read?), `width`
(the text's total advance as Chrome lays it out), or a font-fact kind:
`coords` (normalised variation coordinates), `advances` (per-glyph
advances), `metrics` (line and decoration metrics) or `extents` (glyph ink
boxes); see "Font-fact kinds". The format is extensible: another lower-case
word parses, and is `unsupported` until an oracle and the driver answer it.

|`font`
|yes
|Path relative to the case file (an absolute path is allowed; a missing one
is skipped, as HarfBuzz does for system fonts).

|`font_sha256`
|for corpus fonts
|The font's SHA-256. Required for fonts under `tests/corpus/`; a mismatch
fails the run (`FONT-CHANGED`).

|`text`, `unicodes`
|no (empty text)
|The text, as a string and/or as code points in hb-shape `--unicodes` syntax
(`"U+0041,U+0056"`; `U+`, `u+`, `0x` or no prefix, separated by commas or
spaces; also a list of such strings). When both are given they must agree.
Surrogates and values past U+10FFFF are rejected. Only `shape` and `width`
cases take text.

|`glyphs`
|for `advances`, `extents`
|Glyph ids, `[0, 2, 456]`, or `"all"` (every glyph of the font, in order).
Other kinds take none.

|`face`
|no (0)
|The face of a collection (`ttcf`), as `ReadOptions.face`. Sent to the
oracle as `--face-index=N`; imported HarfBuzz cases spell it that way in
`hb_options`, and a case gives it only once. A face past the font reads as
`read:reject` (roc-font's `NoSuchFace`), also for a single font and face 1.

|`variations`, `variation`, `instance`
|no (Regular)
|Where a variable font is measured; see "Locations". Reading cases take
none; a static font ignores them.

|`options`
|no
|Structured shaping options (next table). Only `shape` cases take them.

|`expected`
|no (`"oracle"`)
|An hb-shape result in glyph-id notation, `read:accept`/`read:reject`/
`read:drop=<tags>`, or `width:<n>`: compared with the record (a mismatch is
`BAD-EXPECTATION`). `"oracle"` (or `"*"`): the record is the only
reference. `"?"`: `record_oracle.py --fill-expected` writes the oracle's
result in its place. An expectation with glyph names is kept but not
compared.

|`reason`, `comment`
|no
|Why the case exists or what it shows.

|`milestone`, `area`, `needs`
|no
|For curated cases: the milestone expected to make it pass, the feature
area, and the capabilities still missing.

|`source`
|no
|Provenance of an imported case: `suite`, `file`, `line`, `case` (the first
16 hex digits of the SHA-256 of the normalised upstream line), `harfbuzz`
(the release) and `expected` (HarfBuzz's own expectation).
|===

=== Locations

Three case fields select a variable font's location, mirroring roc-font's
`Font.Variation` (architecture §5.7, `docs/variable-fonts.adoc` §5.1):

[source,jsonc]
----
{ "id": "office-bold", "text": "office", "variations": {"wght": 700, "opsz": 32} }   // axis tag -> design value
{ "id": "office-named", "text": "office", "variation": {"weight": "Bold", "width": 87.5, "optical_size": 12} }
{ "id": "office-black", "text": "office", "instance": 8 }                             // a named instance index
----

* `variations`: an object of axis tag (1-8 printable characters other than
  space, `,`, `:`, `=`, `\` and quotes) to a number with at most 18
  decimal places (a Roc `Dec`; magnitude at most 10^9). It becomes
  `Font.Variation.{ axes: [...] }` in written order; a later entry wins. A
  tag that is not four bytes, or that the font lacks, is ignored, as
  roc-font ignores it, so a case can show that.
* `variation`: the named-field form, testing roc-font's mapping itself.
  `weight` is `Thin` ... `Black` (CSS 100-900) or an integer 0-65535;
  `width` is `UltraCondensed` ... `UltraExpanded` (CSS `font-stretch`
  percentages, `SemiCondensed` = 87.5) or a percentage; `optical_size` is
  `"FontDefault"` or a size in CSS px (sets `opsz`). `variations` entries
  are applied after these and win per tag.
* `instance`: a named instance index, set on the oracle with
  `hb_font_set_var_named_instance`. It cannot be combined with the other
  two. An index past the font's instances is an oracle `error`.

*The default is Regular, not the default instance.* A case without any of
the three measures at `Font.Variation.{}`: `wght` 400, `wdth` 100 and the
font's default optical size, as a browser does. HarfBuzz's own default is
the font's default instance, which is Light for Merriweather and Fira
Code, so the oracle is never left to its default: `_common.resolve_location`
reads the face's `fvar` and gives the oracle *every* axis at the value the
case selects (unclamped; HarfBuzz clamps as the format defines). The
resolved location is written into the record as `location`:

[source,json]
----
"location":{"axes":[["wght","400"],["wdth","87.5"],["opsz","18"]],"default":false,
            "fields":{"variation":{"width":"SemiCondensed"}}}
----

`fields` are the case's location fields in canonical form (decimal
strings), `axes` the resolved values in `fvar` order, and `default` says
whether every axis is at its default (the protocol 1 driver runs only
those). A static font without location fields gets no `location`, so
records made before locations existed keep their keys. Values are passed
to HarfBuzz as the single-precision number nearest the decimal, as
roc-font converts a `Dec`. At a non-default location every HarfBuzz query
is made twice and the second answer recorded: HarfBuzz quantises a region
scalar in a cache from its second evaluation on, the steady state roc-font
models (`docs/variable-fonts.adoc` §3.3).

=== Font-fact kinds

[cols="1,2,3",options="header"]
|===
|Kind |Takes |Result

|`coords`
|a location
|`coords:<tag>=<F2Dot14>,...`: HarfBuzz's normalised coordinates
(`hb_font_get_var_coords_normalized`, units of 1/16384) in `fvar` axis
order, after `avar`. A static font gives `coords:`.

|`advances`
|`glyphs`, a location
|`advances:<a>,<b>,...`: `hb_font_get_glyph_h_advance` per listed glyph
(`HVAR` at a location).

|`metrics`
|a location
|`metrics:` then `name=value` pairs separated by commas, in the order
`ascent`, `descent`, `line_gap`, `cap_height`, `x_height`,
`underline_position`, `underline_thickness`, `strikeout_position`,
`strikeout_thickness`:
`hb_ot_metrics_get_position_with_fallback` for the horizontal ascender,
descender (negative below the baseline) and line gap, cap and x height,
underline and strikeout offset and size (`MVAR` at a location). The record's
`detail` keeps the values without fallback (null where the font has none).

|`extents`
|`glyphs`, a location
|`extents:` then one entry per listed glyph, separated by a vertical bar:
`<gid>=<x_min>,<y_min>,<x_max>,<y_max>`, the ink box
from `hb_font_get_glyph_extents` (y up), or `<gid>=empty` for a glyph without
outline (HarfBuzz reports a zero box or fails). At a non-default location
this needs `gvar` (phase 3).
|===

All values are font units at a scale of the units per em. Kinds other than
`shape` take no options; `coords`, `metrics`, `advances` and `extents`
take no text.

=== Options

Options are structured; `scripts/_common.py` turns them into the equivalent
hb-shape options, in the fixed order below, for the oracle and the record
key. Shaping cases always carry `--no-glyph-names`; every other kind is sent with its selecting option
(`--read-outcome`, `--width`, `--coords`, `--advances`, `--metrics`,
`--extents`), part of its key, followed by `--face-index=N` for a face
other than 0.

[cols="2,2,1,1",options="header"]
|===
|Field |hb-shape option |Driver |Oracle

|`direction`: `ltr`, `rtl`, `ttb`, `btt`
|`--direction=`
|`ltr` and `rtl` from protocol 3 (`ltr` only before)
|yes

|`script`, `language` (strings)
|`--script=`, `--language=`
|from protocol 3
|yes

|`features`, `variations` (lists of hb-shape items, e.g. `"-kern"`, `"salt=2"`, `"wght=700"`)
|`--features=`, `--variations=` (comma-joined)
|`variations` from protocol 2 (as `axis=` flags), `features` from
protocol 3 (as `feature=` flags)
|yes

|`font_size` (integer)
|`--font-size=`
|when it equals the units per em
|yes

|`cluster_level` (0–3)
|`--cluster-level=`
|0 and 1 from protocol 3
|yes

|`output`: list of `ned`, `no-clusters`, `no-positions`, `no-advances`
|`--ned` …
|yes
|yes

|`utf8_clusters` (bool)
|`--utf8-clusters`
|yes
|yes

|`remove_default_ignorables` (bool)
|`--remove-default-ignorables`
|when the text has no default-ignorable code point
|yes

|`hb_options` (list)
|verbatim (anything else hb-shape takes, e.g. `--single-par`, `--show-flags`)
|`--font-funcs` (`ot` or `ft`) and `--single-par` (no effect on roc-font);
`--face-index=N` from protocol 2
|some
|===

In `hb_options`, `--single-par` is a no-op for the oracle: one buffer is
always one paragraph.

The `variations` option exists for imported HarfBuzz cases; our own cases
use the `variations` case field, which every kind but `read` takes. Both
end up in the resolved location (the option's items after the field's).

When the driver cannot honour an option the review reports
`unsupported:<hb-shape option>` without running the case; when the oracle
cannot, the record's status is `unsupported`.

=== Result notation

Results are `hb-shape`'s text notation (`hb_buffer_serialize`, text format)
with glyph *ids*, because roc-font has no glyph names:

----
[gid=cluster@dx,dy+ax,ay|gid=cluster+ax|...]
----

* `=cluster` is absent with `no-clusters` or `ned`.
* `@dx,dy` (offsets) appears only when one of them is non-zero.
* `+ax` is the advance; `,ay` follows only when the vertical advance is
  non-zero. Advances are absent with `no-advances` or `ned`, and then
  `@x,y` becomes the pen position (the running sum of advances plus the
  offset), as `hb_buffer_serialize` does.
* `no-positions` drops offsets and advances.
* Clusters are *code point indices*; with `utf8_clusters` they are UTF-8
  byte offsets, the unit roc-font's API uses (architecture §5.2).
* Values are font units (hb-shape's default size is the units per em).
* An empty run is `[]`.

Reading results are `read:accept` (the font reads and every table roc-font
reads is usable), `read:reject`, or `read:drop=<tag>,<tag>` (a lenient reader
drops these tables, architecture §4.4; only tables roc-font reads are listed,
sorted). A shaping case whose font is rejected prints `read:reject`.

Width results are `width:<n>`: the advance width of the whole text in font
units with the browser's default features. The driver answers with the sum
of its run's advances (advance plus kerning, as in its shaping result).
On a variable font Chrome keeps each glyph's advance to 1/64 unit, where
HarfBuzz and roc-font round each advance to an integer, so a width case
whose record has a `location` with axes agrees when the two differ by at
most half a unit per glyph (the code point count stands for the glyph
count); everywhere else results compare as strings.

The font-fact results are in "Font-fact kinds" above.

Driver-only results: `unsupported:<option>`, `error:font-file` (the font
could not be read from disk) and `error:malformed-request:<why>`.

== The driver

`tools/driver/main.roc` is a basic-cli app importing `../../package/main.roc`;
`conformance.py` always builds it against the served `roc bundle` output
instead (`--replace-dep`, see below). It reads requests on stdin, one per line, reads each distinct font once (a
cache keyed by path), and prints one line per request in order:

----
request:  <tag> TAB <font path> TAB <kind> TAB <items> TAB <flags>
answer:   <tag> TAB <result> [TAB <reader's problems, with --explain>]
----

* `tag`: an opaque name echoed back; `conformance.py` sends the case id.
* `font path`: as the driver should open it (absolute from the review).
* `kind`: `shape`, `read` or `width`; from protocol 2 also `coords`,
  `advances`, `metrics` and `extents`.
* `items`: lower-case hexadecimal without prefix, comma-separated: the code
  points for `shape` and `width` (empty for empty text), the glyph ids for
  `advances` and `extents` (or the word `all`: every glyph, `0` to the glyph
  count minus one), empty for the other kinds.
* `flags`: comma-separated, from `no-clusters`, `no-positions`,
  `no-advances`, `utf8-clusters` and `font-size=<n>` (the driver answers
  `unsupported:--font-size=<n>` when `n` is not the font's units per em).

*Protocol 2* adds the font-fact kinds and these flags, which only ever
carry the case's own fields (resolving them to axes is roc-font's job, so
the driver tests the mapping):

[cols="1,3",options="header"]
|===
|Flag |Meaning for the driver

|`face=<n>`
|`Font.from_bytes(bytes, ReadOptions.{ face: n })`; absent means face 0.
A face past the font prints `read:reject` like any rejected font.

|`instance=<n>`
|the font at named instance `n` (all its coordinates); never combined with
the flags below.

|`weight=<w>`
|`Font.Variation.weight`: `Thin`, `ExtraLight`, `Light`, `Regular`,
`Medium`, `SemiBold`, `Bold`, `ExtraBold`, `Black`, or a decimal integer
for `Weight(n)`.

|`width=<w>`
|`Font.Variation.width`: `UltraCondensed`, `ExtraCondensed`, `Condensed`,
`SemiCondensed`, `Normal`, `SemiExpanded`, `Expanded`, `ExtraExpanded`,
`UltraExpanded`, or a decimal for `Percent(d)`.

|`optical-size=<s>`
|`Font.Variation.optical_size`: `FontDefault` or a decimal for `Size(d)`.

|`axis=<tag>:<value>`
|one `Font.Variation.axes` entry `{ tag, value }`, `value` a decimal
(`-?[0-9]+(.[0-9]+)?`, at most 18 places); repeatable, in order, a later
entry winning. The tag is passed through unchanged even when it is not four
bytes (roc-font ignores it).
|===

With no location flag the driver measures at `Font.Variation.{}`
(Regular, where `Font.from_bytes` leaves a font), never at the default
instance; this matches the records, because `resolve_location` gives the
oracle `wght` 400 (and every other axis) when a case names no location.
The driver reads each distinct font path and face once and applies a
request's location with `Font.at`, which shares the font's tables. Results of the new kinds use the
notation of "Font-fact kinds" exactly: `coords:` lists every `fvar` axis by
tag in `fvar` order; `advances:` one decimal per requested glyph;
`metrics:` the nine fields in the order shown; `extents:` `|`-separated
entries in request order. Under protocol 1 `_common.driver_request`
answers `unsupported:kind=<kind>`, `unsupported:face` or
`unsupported:location` without sending the case; it runs a case on a
variable font only when every resolved axis is at its default (Inter at
Regular, Merriweather and Fira Code at `wght` 300). `DRIVER_PROTOCOL` in
`scripts/_common.py` names the protocol the driver speaks (2 since
2026-10-24); it is the whole switch on the Python side. An imported case's
`--variations=` values are sent in canonical decimal form (`.3` as `0.3`,
`1.0` as `1`), which denotes the same number.

The driver uses only the public API: `instance=<n>` takes the axis
values `Font.instances` lists (an index past them answers
`unsupported:instance`, which the oracle never records), and `coords`
prints `Font.coordinates`.

*Protocol 3* (since 2026-10-24) adds the shaping options of `shape`
requests, so cases with a script, a direction, features or a cluster level
are measured instead of reported unsupported:

[cols="1,3",options="header"]
|===
|Flag |Meaning for the driver

|`direction=<d>`
|`Font.ShapeOptions.direction`: `ltr` is `LeftToRight`, `rtl`
`RightToLeft`. Vertical directions are answered `unsupported:--direction=ttb`
(or `btt`) without sending the case.

|`script=<code>`
|`Font.ShapeOptions.script`, passed through as written (roc-font
canonicalises ISO 15924 codes as HarfBuzz does).

|`language=<tag>`
|`Font.ShapeOptions.language`, passed through as written.

|`cluster-level=<n>`
|`Font.ShapeOptions.clusters`: `0` is `Graphemes`, `1` `Characters`. Levels
2 and 3 are answered `unsupported:--cluster-level=<n>`.

|`feature=<tag>:<value>:<start>:<end>`
|one `Font.Feature`, repeatable. `value`, `start` and `end` are decimal;
`end` is `*` for the end of the text (`Feature.end`'s default), so
`<tag>:<value>:0:*` is a feature over the whole text. `start` and `end`
count in the units of the request's clusters (code point indices, or
UTF-8 byte offsets with `utf8-clusters`), as hb-shape's feature ranges do.
|===

`_common.driver_features` turns a case's hb-shape feature strings
(`-liga`, `aalt=2`, `kern[3:5]=0`, `kern[3:]`) into flags exactly as
`tools/oracle/extract.py` hands them to HarfBuzz: one entry per tag in
first-seen order, a later global value replacing an earlier one, each
tag's ranges in order, an open range ending at `*` (HarfBuzz's global
end). A feature string the oracle refuses is answered
`unsupported:--features=...`. Tags with `,`, `:` or `*` cannot be carried
and are refused the same way.

*Guessed script and direction.* The oracle shapes with the script and
direction HarfBuzz guesses for the text when a case gives none
(`hb_buffer_guess_segment_properties`), and records them in the record's
`detail` (`{"direction": "rtl", "script": "Arab"}`; `"None"` for no
script). For an imported HarfBuzz case (one whose `source` names a
HarfBuzz version: everything under `harfbuzz/`, `hb-curated/` and
`hb-pending/`), `conformance.py` passes that `detail` to
`_common.driver_request`, which sends the guessed `script=` and
`direction=` where the case has no `script` or `direction`: roc-font does
not detect scripts (that belongs to the `unicode` package), so following
HarfBuzz's guess is what makes the comparison fair. Our own cases are sent
with their own options only, so they test the default path a caller gets.

`_common.driver_request` writes requests; `Case.request` parses them (with
expects for every field and error). By hand:

[source,sh]
----
roc build tools/driver/main.roc --output=.roc-font-tmp/conformance/driver
printf 'x\ttests/fonts/Inter-Regular-metrics.ttf\tshape\t41,56\t\n' | .roc-font-tmp/conformance/driver
# x	[2=0+1273|456=1+1413]
.roc-font-tmp/conformance/driver --explain < requests.txt
roc test tools/driver/Case.roc
----

The driver is a consumer like any other, so it is tested as shipped:
`conformance.py` runs `roc bundle package/main.roc`, serves the bundle from
a loopback address (`scripts/flight.py`) and builds the driver with
`--replace-dep ./package/main.roc <url>`, never from the package's
sources (under `all_tests.py`, from a mirror of the checkout where those
sources are absent). It rebuilds the binary into
`.roc-font-tmp/conformance/` (or `$ROC_FONT_TMPDIR/conformance/`) whenever
a driver source is newer or the bundle differs from the one it was built
against (recorded beside it in `driver.package`), and sends every runnable
case in one process. `--source` builds from `package/` directly, for quick
local iteration only.

Measured on 2026-10-24 with protocol 2: building takes about 7 s; the 6117 requests of
the full local run (our cases, the curated slice and the 6203-case
HarfBuzz import) take 0.12–0.13 s natively (protocol 3: 6623 requests,
0.25 s).

What the driver does with today's public API, and the limits that follow:

* `shape` and `width` call `Font.shape_scalars` with the request's
  `ShapeOptions` (the defaults without shaping flags), passing each code
  point's index (or UTF-8 byte offset with `utf8-clusters`) as its offset,
  so the run's clusters are what hb-shape prints. Vertical text, cluster
  levels 2 and 3, `--remove-default-ignorables` on text with
  default-ignorable characters and font sizes other than the units per em
  stay `unsupported`.
* `advances`, `metrics` and `extents` call `Font.advance`, `Font.metrics`
  and `Font.extents` on the font at the request's location. roc-font's
  descent is a depth (positive below the baseline); the driver negates it
  for the notation. `extents` gives `<gid>=empty` for `Empty`.
* Where the package still measures a variable font at its default instance
  (kerning and glyph boxes, see `Font.at`), cases at other locations are
  known failures until that is wired.

Some nightlies report problems inside the cached basic-cli platform and
exit non-zero although the binary is built.
`conformance.py` accepts that, but fails on any problem reported in this
repository's files.

=== Records and keys

`tests/oracle/records/<case file>.jsonl` holds one JSON object per line,
sorted by case id, with sorted keys and no insignificant whitespace:

[source,json]
----
{"detail":{...},"font":"tests/cases/fixtures/bad-magic.ttf","font_sha256":"8c37…","id":"reading/bad-magic",
 "key":"87a2…","kind":"read","options":["--read-outcome"],
 "provenance":{"backend":"ots-sanitize","extractor":1,"tools":{"ots-sanitize":"9.3.0"}},
 "result":"read:reject","status":"ok","unicodes":""}
----

`status` is `ok`, `unsupported` (the oracle cannot honour an option or
input) or `error` (the oracle failed on this case); the review counts both
non-ok statuses as `unsupported`. `detail` is diagnostic only and never
compared. Records carry no timestamps or machine paths.

Records of `advances` and `extents` cases also carry `glyphs`, and records
on a variable font or with location fields carry `location` (see
"Locations"); other records do not have these fields.

The `key` is a SHA-256 over the canonical JSON of: the font's SHA-256, the
kind, the hb-shape options (derived from the structured options, so their
spelling in the file does not matter; they include the face), the code
points as numbers, the glyph ids (when the kind takes them), the resolved
location (when there is one), the tools that answer this kind with their
versions, and the extractor version of the kind (`EXTRACTOR_VERSIONS` in
`extract.py`: `shape` 2 since `--single-par`, faces and locations, `read`
1, the font-fact kinds 1; `extractor` 2 in `chrome/pin.json` since variable
fonts and collections).
The review recomputes the key from the case, the font and the record's own
provenance, so a stale record is caught without the oracle installed.

=== Recording

[source,sh]
----
python3 scripts/record_oracle.py                   # record cases whose key changed
python3 scripts/record_oracle.py reading           # case files matching "reading"
python3 scripts/record_oracle.py --fill-expected   # also write results into "?" expectations
python3 scripts/record_oracle.py --check           # fail if a record is missing or stale
python3 scripts/record_oracle.py --force           # re-record everything
----

Records whose key is unchanged are kept; records for cases that no longer
exist are pruned; a case whose font is missing keeps its old record.
`--force` must reproduce every file byte for byte (checked on 2026-10-24 for
every record file, 6706 records including the Chrome width records at
variable-font locations), and any difference is a reproducibility bug. `--fill-expected` calls
`_common.fill_expected(path, {case id: result})`, which finds each case by
its `"id"` text and replaces the first `"expected": "?"` after it, keeping
comments and layout.

== The review

`scripts/conformance.py` compares the driver's result for each case with its
record.

=== Gating and scored suites

A case file *gates* unless `tests/scores.json` declares it *scored*: its
`scored` list holds path prefixes under `tests/cases` (today `harfbuzz/`,
the full HarfBuzz import, and `hb-pending/`, curated cases a later milestone
will make pass). A scored *suite* is the prefix's directory plus one more
path component (`harfbuzz/in-house`, `hb-pending/M4`).

Gating cases:

[cols="1,3",options="header"]
|===
|Outcome |Meaning

|agree |the result equals the record
|known |differs, and `tests/known-failures.json` lists the case
|FAIL |differs and is not listed
|STALE |listed but now agrees, listed but no such case exists, or listed but scored
|MISSING-RECORD |no record, or its key no longer matches the case or font
|MISSING-FONT |a font inside the repository is missing
|FONT-CHANGED |the font's SHA-256 differs from the case's `font_sha256`
|BAD-EXPECTATION |the case's own glyph-id expectation differs from its record
|unsupported |the driver or the oracle cannot honour an option yet
|skipped |a corpus font that has not been fetched, or a missing system font
|===

Scored cases count as agree, differ, unsupported or skipped per suite and
never need a known-failures entry; MISSING-RECORD, MISSING-FONT,
FONT-CHANGED and BAD-EXPECTATION fail there too. Each fully selected
suite is compared with its entry in `tests/scores.json`, a ratchet like the
allocation baseline (architecture §9.2):

[cols="1,3",options="header"]
|===
|Outcome |Meaning

|SCORE-DROP |fewer cases agree than recorded: a regression, fails
|SCORE-CHANGED |more agree, the same number but a different agreeing set
(`agree_ids` digest), or other counts moved: fails until `--update-scores`
locks it in
|SCORE-NEW |a suite with no recorded score: fails until recorded
|SUITE-CHANGED |the suite's cases differ from the recorded ones
(`case_ids` digest), as after importing another HarfBuzz release
|===

A suite listed in `scores.json` with no case files here (the HarfBuzz import
is git-ignored) is skipped with a note, never a failure; so is a suite
whose skipped count differs from the recorded one (corpus not fetched,
system fonts present) or one only partly selected.
`python3 scripts/conformance.py --update-scores` records every fully run
suite and prints what changed; the diff of `tests/scores.json` is the
review. Recorded on 2026-10-24:

[cols="2,1,1,1,1,1",options="header"]
|===
|Suite |Cases |Agree |Differ |Unsupported |Skipped

|harfbuzz/in-house |5174 |82 |4706 |241 |145
|harfbuzz/aots |276 |0 |0 |276 |0
|harfbuzz/text-rendering-tests |753 |122 |137 |494 |0
|hb-pending/M1-next |22 |0 |22 |0 |0
|hb-pending/M3 |86 |0 |12 |74 |0

Upper-case outcomes fail the run; `--strict` makes gating `unsupported`
fail too. Options: case-file selectors (substrings of paths under
`tests/cases`), `--diff`, `--verbose`, `--explain`,
`--rebuild`, `--no-build`, `--update-scores`, and `--json <file>` (every
case's outcome, expected and actual result, for triage and curation).

=== Known failures

`tests/known-failures.json` lists `{ "id", "reason" }` entries, sorted by
id. The policy, as in roc-parser:

* Every gating difference is either fixed or listed with a reason a reader
  can act on: which behaviour differs and why (not implemented yet, with the
  architecture section; or deliberate, with the justification).
* A listed case that starts to agree fails the run, so the list cannot rot.
* Scripts never edit the list. Removing or adding an entry is a reviewed
  change.
* An entry names one case. There are no patterns.
* Scored cases are never listed; promote a case to gating first.

=== Importing all of HarfBuzz's shaping tests

[source,sh]
----
python3 scripts/fetch_corpus.py fetch harfbuzz-14.6.0
python3 scripts/fetch_corpus.py import-hb-tests --suite in-house --suite aots --suite text-rendering-tests
python3 scripts/record_oracle.py harfbuzz
python3 scripts/conformance.py harfbuzz --explain
----

`import-hb-tests` converts each `.tests` file into
`tests/cases/harfbuzz/<suite>/<name>.jsonc`. Each case line (as HarfBuzz's
`run-tests.py` reads it: `font;options;code points;expected`, skipping
comments, disabled cases and `@` directives) becomes a case object: the
font path relative to the new file with its `font_sha256`, the code points,
the hb-shape options parsed into structured fields (anything without a field
goes to `hb_options`), the expectation when it is written in glyph ids
(otherwise `"oracle"`), and `source`. The case id is `c` plus 12 hex digits
of the normalised line's hash, so ids survive lines moving; identical lines
get `-2`, `-3`. The result is git-ignored and scored. Cases naming macOS
system fonts are skipped where those fonts are absent.

Measured on 2026-10-24: 6203 cases in 308 files; the oracle recorded 6058
(35 use options the extractor does not support, such as `--font-ptem`,
`--shaper=` and `--unicodes-before`, and the space-separated
`--variations wght=700`; 4 make HarfBuzz fail; 145 name macOS system
fonts). AOTS's `--single-par` and the collections' `--face-index` are
supported since extractor `shape` 2; 264 records are on variable fonts and
carry a resolved location. The
driver (protocol 2) agreed on 424, 805 were unsupported (an option the driver or the oracle cannot honour yet), and 4829
differed, 3825 of them because AdobeBlank2 maps everything through cmap
format 13, which the reader rejects. With protocol 3 (2026-10-24), which
passes the case's shaping options and HarfBuzz's guessed script and
direction, AOTS went from 276 unsupported to 203 agreeing (the 71 that
differ are GPOS lookups other than pair adjustment and cmap glyph ids past
the glyph count), in-house measured 56 more cases (4091 agree, 870
differ, 68 unsupported) and text-rendering-tests agree on 232. In-house
lost 109 agreements that had held only because the script was not passed:
the Tibetan cases, whose fonts list their substitutions under `DFLT`
`rlig` as well as under `tibt` `abvs` and `blws`; with the guessed script
`Tibt`, roc-font's default shaper chooses `tibt` and does not turn on
`abvs` and `blws`, which HarfBuzz's complex-script shaping does. The
differing in-house cases are complex scripts (667), GPOS beyond pair
adjustment (37), variations (9), AAT (4) and other (153, mostly Thai

=== Curated imports

Our own case files are the authority; HarfBuzz's suites are sources we
curate from. `tests/cases/curated.jsonc` lists the cases in scope, each with:

[source,json]
----
{ "id": "aots-gsub1-1-simple-2", "suite": "aots", "file": "gsub1_1_simple.tests", "line": 2,
  "case": "354f8418d8c1b4b1", "area": "gsub-1", "milestone": "M3", "gating": false,
  "needs": ["feature selection", "oracle --single-par"],
  "reason": "AOTS gsub1 (gsub1_1_simple_f1): the basic case; the test feature selects the lookup" }
----

`case` is the first 16 hex digits of the SHA-256 of the normalised line
(fields stripped, whitespace collapsed). The importer uses `line` when the
hash matches there, otherwise the nearest line with that hash (and asks for
`line` to be updated); a hash found nowhere fails the import. `milestone` is
the `TODO.md` milestone expected to make the case pass (`M1-now` passes
today, `M1-next` lands with work in progress, `post-0.1` after 0.1.0).
`fonts` pins every font used by SHA-256 and size; `font_size_cap` (65536)
bounds committed fonts. The list is JSONC, but `--pin-fonts` rewrites it in
canonical form keeping only its header comment, so explanations belong in
`reason`.

[source,sh]
----
python3 scripts/fetch_corpus.py import-hb-tests --curated              # write the curated files
python3 scripts/fetch_corpus.py import-hb-tests --curated --check      # fail if they are out of date
python3 scripts/fetch_corpus.py import-hb-tests --curated --pin-fonts  # pin new fonts, drop unused pins
python3 scripts/record_oracle.py hb-curated hb-pending
----

Entries with `"gating": true` go to `tests/cases/hb-curated/<suite>.jsonc`
and must agree like any of our cases; the rest go to
`tests/cases/hb-pending/<milestone>.jsonc`, scored suites whose agree counts
ratchet. Gating cases' fonts up to the cap are copied into
`tests/cases/hb-fonts/<suite>/` with the suite's licence; pending cases and
larger fonts read the fetched corpus and are skipped without it. The
importer owns those three directories (it removes anything it did not
write), changes nothing on a re-run, and refuses to write if any font
differs from its pin.

To promote a case once its milestone lands: set `"gating": true`, re-import,
record, and run the review (`SCORE-CHANGED` for the pending suite then asks
for `--update-scores`). To add one: find it with `conformance.py --json`,
add an entry, re-import with `--pin-fonts` and record.

== Extending the harness

Adding a case:: add an object with an `id` and `"expected": "?"` to a
`.jsonc` file; run `record_oracle.py --fill-expected <file>`, read the
result, and commit the case and its record together. If roc-font disagrees
on purpose, add a known-failures entry with a reason.

Adding a case source:: a converter that writes `.jsonc` files under
`tests/cases/<source>/` in this format, with fonts committed under
`tests/fonts/` (small, with a licence) or pinned in `tests/corpus.json` and
named with `font_sha256`. Prefer one re-runnable importer per upstream
suite, with the upstream version in `source`. Declare it scored in
`tests/scores.json` until it can gate.

Adding an oracle or case kind:: pin the tool, report its version, add the
kind to `KNOWN_KINDS` and its selecting option to `hb_options` (via
`FACT_OPTIONS` for a font fact) in `scripts/_common.py`, give it an
extractor version in `EXTRACTOR_VERSIONS`, teach `record_oracle.py` which
oracle answers it, add a result notation that cannot be confused with
hb-shape output, support it in the driver protocol (`Case.roc`,
`_common.driver_request`), and document it here. Re-record with `--force` twice and confirm the second run changes
nothing.

== Known environment issues

* Some nightlies report type problems inside the cached basic-cli
  platform and exit 1 although the binary builds correctly (nightly-2026-10-23
  did with basic-cli 0.23.0); `conformance.py` tolerates exactly that.
* An older local debug compiler (debug-7894793d) panics in its ARC
  certification pass when building any app that calls `Font.from_bytes`
  (including the driver). Use the latest nightly.
* Width cases need Node 22 or later (`width.mjs`); Node 18 fails.

== Resource-limited partial runs

`ShapeLimits` uses the pinned reference's growth and operation factors,
but counts the lookup and script work documented by the public API.
HarfBuzz additionally debits its buffer cluster merges, flag spans and
copying. After either counter is exhausted, the engines can have made
different partial progress. Such a partial run does not establish a
successful shaping difference.

The context-positioning fixtures retain actual HarfBuzz partial results and
declare two mixed-advance work-accounting divergences explicitly. A separate
literal call-graph interpreter checks Roc's stopped position and
`Operations` report; the verifier still compares every other field and
requires exact agreement for the completed cases. The adjacent source probe
records the reference's two grapheme-merge and three attachment-flag charges.
No reference result is replaced with a Roc-generated golden.
